# Lessons

- Worktrees: if the user asks for a worktree, create a real git worktree with `git worktree add` under `.worktrees/`. Never use a branch in the active tree as a substitute.
- Worktree results: NEVER apply work from a worktree back to the main working tree without explicit user confirmation. Leave changes in the worktree and ask the user how they want to proceed (cherry-pick, patch, keep worktree alive, etc.).
- `void.json` changes: update `framework/packages/void/schema.json`, `framework/docs/config.md`, and any related types, validation, or README references.
- Drizzle `push` -> `migrate`: if the schema was created with `drizzle-kit push`, seed `drizzle.__drizzle_migrations` from `drizzle/meta/_journal.json` before switching to `drizzle-kit migrate`.
- Cloudflare Workers + CJS: when Vite/Rolldown bundles CJS packages for Workers, add `esmExternalRequirePlugin` to the actual worker environment in `vite.config.ts`. The env name is the Wrangler worker name, not `"ssr"`.
- Dual SQLite/Postgres features: keep dialect-specific imports in dialect-specific modules. Do not put `pg` imports or PostgreSQL-only dynamic imports in shared code that is also used by D1/SQLite paths, or Workers bundles will pull `pg` into the SQLite branch and emit Node builtin import warnings.
- Schema deploy safety: migrations must remain backward compatible while old code is still running. Additive changes are safe; renames, drops, and type changes need a two-phase rollout. Use `VOID_TEST_DATABASE_URL` for real-Postgres compat checks and keep `fileParallelism: false`.
- Git commit HEREDOCs: avoid apostrophes in `git commit -m "$(cat <<'EOF' ...)"` messages, or avoid that pattern entirely.
- `pnpm test` filtering: run `pnpm test <path-or-pattern>` without `--`.
- Cloudflare Analytics Engine SQL: include `timestamp` in `SELECT` if you filter or sort on it, use `GROUP BY` instead of `DISTINCT`, cast with `toDateTime(...)`, do not alias over `timestamp`, and format datetimes as `YYYY-MM-DD HH:MM:SS`.
- Docs sweeps: code is the source of truth for implemented behavior, but public docs can intentionally omit paused features. Describe root scripts exactly as implemented; in this repo, root `dev` and `build` are dashboard-only unless source changes.
- Pre-launch transitions: if the user says a feature is not live yet, prefer a clean cutover over legacy migration work.
- Design doc revisions: stay in design/doc mode until the user explicitly asks for implementation.
- Framework DX design: preserve existing CLI namespaces, prefer convention over configuration, keep advanced hooks as escape hatches, and honor explicit clean breaks instead of carrying legacy surfaces forward.
- Integration ownership in design work: if the user distinguishes v1 app-owned integration from later platform-managed integration, reflect that split directly and do not add a temporary platform-owned stub unless asked.
- Playground UI: match the existing minimal demo style unless the user explicitly asks for design work.
- Clean-break docs: document only the new surface by default. Mention removed or deprecated keys only when the user asks for migration guidance.
- Support package surfaces: when moving adapter or plugin packages, keep runtime APIs at the package root and move Vite plugin factories to explicit `/plugin` subpaths instead of mixing both on the root import.
- Framework full build: in `framework/`, use `pnpm build:all` for a full build. `pnpm build` is packages-only.
- Drizzle validators: on `drizzle-orm@0.45.x`, use `drizzle-zod`, `drizzle-valibot`, and `drizzle-arktype`, not `drizzle-orm/*` validator entrypoints.
- SQLite PRAGMA syntax: use bare names or single-quoted strings for `PRAGMA table_info(...)` / `PRAGMA index_list(...)`; do not pass double-quoted SQL identifiers there.
- Schema-derived validator requests: when the user asks for inferred validators, define them from the Drizzle schema in `db/schema.ts` via `void/drizzle-valibot` and import them from `@schema` instead of hand-writing Valibot object schemas in the handler.
- Progress docs: do not mark a feature done just because code or a package exists. For product-readiness tracking, treat "implemented", "shipped", and "done for milestone" as separate states unless the user confirms they are equivalent.
- Migration-binding consistency: `packageBuild` and `packageFrameworkBuild` must include the database binding in the manifest whenever migrations are present, even if source-code inference sets `needsD1: false`. Migrations on disk imply a database is needed. The condition is `bindings.needsD1 || bindings.needsAuth || hasMigrations`. Note: for PostgreSQL, this does not cover the CLI-side Hyperdrive pre-provisioning prompt (which runs earlier in deploy.ts before migrations are collected); server-side provisioning throws a clear error if Hyperdrive was never set up.
- Deploy cancellation: use a two-phase cancellation state. A cancel request must remain active/blocking until the running deploy pipeline observes it and finishes cleanup; ordinary status updates must not overwrite cancellation requests before they become terminal.
- Deploy dedupe: asset manifests alone are not enough to prove worker-backed deploys are identical. Only skip worker deploys when worker module content hashes are part of the comparison; otherwise keep identical fast paths static-only.
- Deploy asset hashing: never trust client-declared content hashes for uploaded blobs based on size alone. Verify the declared hash against the uploaded bytes, preferably with streaming/chunked hashing to avoid Worker OOM.
- Deploy WfP asset uploads: do not build Cloudflare asset upload `FormData` from base64 strings inside the API Worker. Stream multipart bodies and base64-encode blob chunks on demand; otherwise large media-heavy deploys can still OOM after request parsing and hashing.
- CF assets-upload-session dedupe poisoning (cloudflare/workers-sdk#12586, internal WC-4511): CF's WfP asset session can claim hashes are already cached when the bytes are not actually present, leading to deploys that ship workers serving the 36-byte `Assets have not yet been deployed...` stub. Mitigations in `packages/api/src/routes/deploy.ts`: (1) inject a per-deploy `/.void-deploy/<deploymentId>.txt` cache-buster before `createAssetUploadSession` so each session always carries one novel hash and CF re-validates the full manifest — still required; (2) early `asset_hashes` persistence so a late-step failure doesn't permanently deadlock the project. As of 2026-04-23, runtime safety-net added in `meta/design-docs/0066`: every WfP deploy also mirrors assets to `STATIC_ASSETS`/`STATIC_ASSETS_R2`, and `packages/dispatch` detects the CF stub (status 200 + `text/plain` + body marker) and serves from the mirror. CF bug still exists upstream; this masks the user-visible symptom. Static-only deploys (KV/R2 path) bypass the buggy CF API and don't need any of this.
- Smoke-test staging routing: the framework CLI's `isVoidInternalStaging` only reads `voidInternalStaging` from `.void/project.json` (gitignored), and nothing in `framework/packages/void/src` reads `process.env.STAGING`. CI must set `VOID_API_URL=https://api.staging.void.cloud` explicitly; `STAGING=1` alone is a no-op despite older docs.
- Staging is gated by Cloudflare Access (GitHub organization `voidzero-dev` via GitHub as the IdP) — any programmatic caller hitting `api.staging.void.cloud`, `proxy.staging.void.cloud`, `dash.staging.void.cloud`, or `*.staging.void.app` must present CF Access credentials. Resolution priority in `framework/packages/void/src/shared/cf-access.ts`: (1) `CF_ACCESS_CLIENT_ID` + `CF_ACCESS_CLIENT_SECRET` → service-token headers (CI), (2) `CF_ACCESS_TOKEN` → `cf-access-token` user-JWT header (dev). The Void CLI eagerly probes `cloudflared access token -app=<api-url>` at `PlatformClient` construction (`framework/packages/void/src/cli/cf-access.ts`), auto-running `cloudflared access login` on interactive shells when no cached JWT exists; teammates need only `brew install cloudflared`. Runtime clients (`runtime/remote/client.ts`, `runtime/ai.ts`) read from the same helper. OAuth callback paths (`/auth/callback`, `/admin/callback`) are Access-bypassed because IdP redirects cannot carry service tokens. Production is not gated.
- Deploy corroboration backend classifier: `deploymentBackendKindFromManifest` in `packages/api/src/routes/deploy.ts` treats pre-`type` manifests (no `type`, no `framework`) as WfP by default. This is intentional but imprecise: legacy static uploads can also have an untyped manifest (the server's `isStaticOnly` branch derives mode from `assetConfig.not_found_handling`). Collision requires a project that has a retained pre-`type` static row AND is now deploying WfP AND shares a hash AND CF claims it cached — vanishingly rare in practice, so accept it rather than re-derive mode on every corroboration read. If this ever bites, add a `deployments.mode` column and backfill from `manifest.assetConfig` / worker-file presence at read time.
- Cloudflare Durable Object integrations: when multiple features share Worker upload migrations, preserve chronological migration tag order across feature namespaces, and ensure generated Worker exports plus runtime helpers use configured class and binding names rather than default constants.
- Cloudflare DO namespace lookup for WfP scripts: never poll the account-wide `GET /workers/durable_objects/namespaces` endpoint to discover a per-script DO namespace ID. CF silently ignores `?script=` filters there, so the lookup is global, races against propagation lag, and ages out at the retry budget. Use `GET /workers/dispatch/namespaces/{ns}/scripts/{script}/bindings` instead — it returns the binding's `namespace_id` directly the moment the script upload is acknowledged, so the only thing your retry loop has to absorb is the worker upload itself becoming readable.
- Cloudflare workerd / WfP dispatch from inside a Durable Object: as of the wrangler `^4.84.x` and `@cloudflare/workers-types ^4.20260424.x` rollout, calling `env.DISPATCH.get(name).fetch(req)` (or any service-binding `.fetch`) from inside a `DurableObject`/`WorkerEntrypoint` subclass dispatches with `entrypointName` set to the _calling_ class's name. Workers that don't export a matching named entrypoint fail with `The entrypoint name X was not found in this worker.` (`workerd/src/workerd/io/worker.c++:2391-2401`). Workaround: never dispatch from inside a DO method. Defer to a CF Queue (the queue handler runs as a fresh non-RPC fetch event with no class context) or a separate non-DO worker via service binding. The platform uses this pattern in `packages/api/src/cron-fires-queue.ts` for cron triggers — the DO enqueues, the queue handler dispatches.
- Cron-DO sync must run AFTER the routing switch so that pre-cutover failures (ISR clear, prerender, retention cleanup planning, etc.) don't disable the still-live previous deployment's crons. If cron sync runs before the switch and a later step throws, the catch path would `/clear` or leave the DO pointing at a worker we are about to tear down. Running `/sync` (or `/clear`) only after `routingSwitched = true` keeps the previous cron state untouched until the new routing has actually replaced it. A post-routing sync failure is logged and tolerated — the deploy is already live and the next deploy resyncs. See `packages/api/src/routes/deploy.ts` step 5c.
- `void project logs` only sees what Cloudflare Tail captures — top-level `console.*` calls and uncaught throws. Application-level errors caught and persisted to the user's own DB are invisible. Surface them via `console.error` or `void/log`'s `logger.error(...)` so they appear under `--level error`. Also: `--filter` is a substring search over log message text and exception name/message, NOT a level filter — use `--level <error|warn|info|log|debug|all>` for level filtering.
- Cloudflare WfP container application provisioning: CF does **not** auto-create container applications from a worker's `containers: [{ class_name }]` upload metadata. The platform must POST `/accounts/{acct}/containers/applications` itself with the full `CreateApplicationRequest` body — including `durable_objects: { namespace_id }` — matching wrangler's reference flow (`workers-sdk/packages/wrangler/src/containers/deploy.ts` `apply`, `workers-sdk/packages/containers-shared/src/client/models/CreateApplicationRequest.ts`). PATCH bodies must omit `durable_objects` and `name` (neither is in `ModifyApplicationRequestBody`); the DO binding is set at POST time and is immutable afterwards. Race handling: HTTP 409 is the authoritative "concurrent create" signal — fall back to re-find + PATCH; message-text matching for `already exists` / `duplicate` is defense-in-depth only (avoid generic words like `conflict` that collide with unrelated CF validation errors). Before PATCHing an existing same-name app, verify `existing.durable_objects.namespace_id === config.namespaceId` and fail loudly on mismatch — silently PATCHing a stale or rotated same-name app sends sandbox traffic to the wrong DO. See `packages/api/src/provisioning/containers.ts` `upsertSandboxContainerApplication`.
- Production-backed local dashboard testing: when gating on a newly-added API response field, remember production may not have that field until the API is deployed. In local dashboard dev, prefer a localhost-only access bypass over a committed or ad hoc allowlist.
- Dashboard Worker local env: if `packages/dashboard/.dev.vars` exists, do not rely on one-off shell env vars reaching Miniflare Worker bindings. Put local dashboard-only vars such as `API_URL` and `SITE_DOMAIN` in `.dev.vars` or `wrangler.jsonc` vars before debugging auth behavior.
